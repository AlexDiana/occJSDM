# Parallel MCMC chains for runOccJSDM()

Date: 13 October 2026. Status: design agreed in conversation with Doug on 13 October 2026, provisionally; written for Doug's review, including an external review he will commission, before an implementation plan is made. Nothing has been implemented or run. This is the `TODO.md` item "Run MCMC chains in parallel" under *Needed for the paper*. It will go to Alex as a pull request against `AlexDiana/occJSDM`, in the style of PR #14.

## Purpose

`runOccJSDM()` runs its MCMC chains one after another in one process. This design runs them on separate cores, one chain per worker process at a time, with reproducible per-chain seeds, an explicit core budget, and exact combination of the posterior arrays, the latent-state means and the WAIC accumulators. The result of a fit must not depend on how many workers ran it.

Why now, decided 13 October 2026: the paper's simulation study should run on the code that ships, so that its validation also covers the chain-combination code. The production simulation run waits until Alex merges this. Parallel chains will not speed that study, which already parallelises over replicates; the gain is for users, lesson builds and small studies.

## What the code does today

Verified on 13 October 2026 against `main` at `d72daaf`. Line numbers refer to `R/runOccJSDM.R`, which no commit since `880ddb0` touches.

- Line 1051 calls `setOccJSDMSeed(sample.int(.Machine$integer.max, 1L))` once per fit, seeding the C++ Mersenne-Twister stream in `src/rng.h` from R's RNG. Then `for (chain in 1:nchain)` at line 1053 runs the chains serially. Every chain resets to identical starting values (lines 1095 to 1199), so chains differ only by their stretch of the stream.
- A chain also consumes R's own RNG, not only the C++ stream: `sample_theta0()` draws with `rbeta()` (`R/mcmcfun.R` line 24), the inverse-gamma draws go through `R::rgamma()` under an `RNGScope` (`src/jsdm.cpp` line 286), and the length-scale index uses `sample.int()` (`R/jsdmfun.R` line 1211). Per-chain seeding therefore has to set both generators at the start of every chain.
- Posterior draws are stored per chain in `*_output_chain` arrays and copied into full arrays with trailing dimensions `[..., niter, nchain]` after each chain (lines 1367 to 1402).
- With `summarisedLatentPresences = TRUE`, the default, the latent-state means of `z`, `psi`, `theta` and `w` accumulate inside the loop as `(1 / (niter * nchain))` times the value, once per retained iteration (lines 1296 to 1314). `theta` and `w` are always returned as means; only `z` and `psi` have a full-array option.
- The legacy complete-data WAIC accumulates across all chains with `update_waic_summary()` (`R/mcmcfun.R` line 35), which keeps per observation a running mean of the log-likelihoods, a running sum of squared deviations (`M2`) and a running mean of the likelihoods, updated with a counter that runs from 1 over all chains (lines 1340 to 1360). `compute_waic()` (`R/mcmcfun.R` line 56) finalises it with `niter * nchain` draws (lines 1406 to 1420). `computeSiteWAIC()` in `R/site-waic.R` works on the stored arrays and indexes draws as iteration within chain, so it is unaffected by how the chains were run.
- `reparamFactorModel()` (`R/jsdmfun.R` line 6) rotates each draw separately, so it can stay in the parent after combination and cannot depend on the worker count.
- The roxygen `@details` (lines 449 to 455) say random draws run serially on the main thread whatever the RcppParallel thread count. That is correct. `tests/testthat/test-rng-safety.R` was run against the installed 0.1.1 build on 13 October 2026 and all 29 assertions pass, including fits bit-identical at 1 and 4 threads for the binary, continuous, occupancy and two-stage models. `AGENTS.md`'s August 2026 statement that fits are bit-reproducible only at one thread (the section "Detail behind Fixed bugs 40-42", and the Fixed bugs 41 advice to set `RCPP_PARALLEL_NUM_THREADS=1`) is stale; it was superseded by Fixed bugs 50 on 14 September 2026.
- A pre-existing oddity: with `summarisedLatentPresences = FALSE`, a per-chain `theta_output_chain` array is allocated (line 1063) but never written or read; `theta_output` is always the posterior mean.
- `.onLoad()` in `R/zzz.R` sets `options(mc.cores = 2)`. Nothing in the package reads it, and this design does not use it.

## Decisions made on 13 October 2026

- The worker count lives in `MCMCparams$ncores`, default 1, so fits are serial unless asked.
- `ncores` is the total core budget: workers = min(nchain, ncores), and each worker gets floor(ncores / workers) RcppParallel threads.
- A parallel fit shows a progress file plus a summary. The start message includes the `tail` command.
- The shipped `sampleresults` is refitted in this pull request under the new code.
- Architecture: one single-chain function, driven in process one chain at a time for serial fits and by `clusterApplyLB()` on a PSOCK cluster for parallel fits, one chain per task. Two alternatives were considered. Recursive single-chain calls of `runOccJSDM()` stitched together by the parent were rejected because the data preparation would repeat per chain, the scalar WAIC cannot be merged exactly, and the serial path would also have to recurse. Partial combination inside the workers was rejected as premature because the parent holds every chain's arrays either way.
- Doug's approvals are provisional until this spec has been through an external review.

## Non-goals

- No redesign of the random streams within a process, and no stream splitting. Independence between chains comes from distinct seeds on two Mersenne-Twister generators.
- No dispersed starting values. The mirror-labelling check in `TODO.md` remains a separate item.
- No change to the sampling order within an iteration, to any sampler, prior or default other than `ncores`.
- No fail-fast across chains beyond what base `parallel` allows.
- No change to the lessons' teaching archives, and no `TODO.md` edit in the pull request.
- No Windows benchmark. The mechanisms are cross-platform, and the report says it was not run there.
- No dependency beyond base `parallel` and `tools`. `pkgload` is used only when the parent itself was loaded by it, and is listed under `Suggests` because `R CMD check` warns on a qualified call to an undeclared package (found during implementation, 13 October 2026); it is never required for an installed package.

## Interface

- `MCMCparams$ncores`, read with `get_param()` like `nchain`, default 1. It must be a single whole number of at least 1, otherwise an error. Above `parallel::detectCores()` it warns and proceeds.
- Budget rule: workers = min(nchain, ncores). Each worker gets floor(ncores / workers) RcppParallel threads, at least 1, set in the worker through the `RCPP_PARALLEL_NUM_THREADS` environment variable alone. That variable is all `RcppParallel::setThreadOptions()` itself sets for the thread count (checked 13 October 2026), and that function would also unset `RCPP_PARALLEL_STACK_SIZE` through its default, so it is not called: a custom stack size the session has set is left alone, in the workers, which inherit it, and in the in-process pin. Any remainder of the budget is idle; for example `ncores = 3` with two chains gives two single-threaded workers. The budget governs processes and RcppParallel threads. It does not govern a multithreaded BLAS or LAPACK, which the sampler's R-level matrix algebra and Armadillo's dense algebra both call. Workers are asked to run their BLAS single-threaded, whatever `ncores` says: the parent sets `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS` and `VECLIB_MAXIMUM_THREADS` to 1, and `MKL_DOMAIN_NUM_THREADS` to `MKL_DOMAIN_ALL=1` because Intel documents the domain variable as overriding the plain one, in its own environment for the duration of `makeCluster()`, since a worker's BLAS reads them at process start, and restores its environment afterwards; the parent's own BLAS, already loaded, is unaffected. These settings are requests, not proof. Base R cannot query a loaded BLAS's thread count, other variables can override these for some libraries, and the parent's own already-loaded BLAS can be neither reconfigured nor inspected, so the package verifies nothing about the BLAS. R's reference BLAS is single-threaded by construction, and `extSoftVersion()` naming `libRblas` indicates it, but only indicates: R's own documentation for `extSoftVersion()` notes that an external BLAS copied, hard-linked or renamed into place also appears as `libRblas`, and the name is uninformative on Windows and with Accelerate. Provenance is established outside the package, by inspecting the library file, as described under *Tests*, and declared to the package through an environment variable, `OCCJSDM_REFERENCE_BLAS`, which only provenance-checked environments set. Pinning to 1 rather than to the per-worker budget is deliberate: a BLAS thread count that varied with `ncores` would make floating-point results vary with it, and the sampler's matrices are small enough that a threaded BLAS gains nothing. The package's own C++ has no OpenMP regions (every pragma in `src/` is commented out), so `OMP_NUM_THREADS` affects only BLAS builds that honour it. None of this is verified against a threaded BLAS here, because this machine's R 4.6.1 uses R's reference BLAS and LAPACK (`libRblas`, `libRlapack`). The help page says so, and the execution record names the BLAS and LAPACK in use and separates what was requested from what was declared.
- `ncores = 1` is today's fit: in process, with the session's RcppParallel setting untouched. Its execution record reports the ambient RcppParallel thread count, the environment variable if set and otherwise `RcppParallel::defaultNumThreads()`, labelled as ambient rather than as a budget.
- `ncores > 1` with `nchain = 1` also runs in process, with the session's RcppParallel thread count set to `ncores` for the fit and restored afterwards, so the budget means the same thing everywhere except the untouched default.
- Messages. "Running MCMC" is printed as today. When a cluster is used, that is when workers > 1, the parent then prints one start line, for example "Running 4 chains on 4 workers, 1 RcppParallel thread each. Follow progress with: tail -f /path/occJSDM-progress-1a2b3c.log". The workers' existing "Chain k - Iteration n" and burn-in messages, printed every 100 iterations, go to that file. In both modes the parent prints one line per chain with its elapsed time once the chains have finished, for example "Chain 1 finished in 312.4 s". For an in-process fit, whatever `ncores` says, the chain messages print to the console as today, there is no start line and no progress file, and the execution record has `progress_file = NULL`.
- The progress file is `tempfile("occJSDM-progress-", fileext = ".log")`. It is not deleted; the session's temporary directory goes when R exits.
- The returned object's `infos` gains three fields, for provenance and for rerunning one chain; nothing in the package reads them. `MCMCparams` holds the resolved sampling settings: `nchain`, `nburn`, `niter`, `nthin`. `chain_seeds` is a 2 by `nchain` integer matrix with rows `r` and `cpp`. `execution` records how the fit was run and is the only part of the object that may differ between core counts: `ncores`, `workers`, `threads_per_worker`, `thread_setting` ("budget" or "ambient"), `blas_threads_requested` (the thread variables set for the workers, or `NULL` for an in-process fit), `worker_pids` (the worker process ids, or `NULL`), `blas_declared` (`TRUE` when the session declared a provenance-checked single-threaded BLAS through `OCCJSDM_REFERENCE_BLAS`, otherwise `FALSE`; the package itself never sets it), `blas` and `lapack` from `extSoftVersion()` and `La_library()`, `elapsed` (seconds per chain) and `progress_file` (`NULL` for an in-process fit). Wherever this design says two fits are identical across core counts, it means identical after dropping `infos$execution`, with the execution fields checked separately for their expected values. A small internal helper does the dropping, so that the tests, the benchmark and the refit use one definition.
- The roxygen promise that the calling session's RcppParallel thread setting is preserved stays true in every mode.

## Seeding and reproducibility

- Where seeds come from. After the existing setup and before any chain runs, the parent draws `2 * nchain` distinct integers with `sample.int(.Machine$integer.max, 2L * nchain)` from R's RNG, in whatever state the user left it. Chain k receives an R seed and a C++ seed. The parent then saves `.Random.seed`.
- What a chain does with them. At its start a chain calls `set.seed()` with its R seed and the kinds pinned to Mersenne-Twister, Inversion and Rejection, then `setOccJSDMSeed()` with its C++ seed. Pinning the kinds means a worker, whose fresh session has R's defaults, and the parent, whose session may be in any kind, produce the same R-level draws.
- After the chains. Both paths leave the parent's RNG in the same state by doing the same two things to it, in the same order, in one cleanup handler that runs on every exit: one `set.seed()` with the pinned kinds, then assignment of the saved `.Random.seed` in the global environment, which restores the value and the RNG kinds. The handler is registered with `on.exit()` immediately after the save, before any chain runs or any cluster exists, and both steps live in it, so the parent's final RNG state is the same whether the fit completed, a chain errored, the dispatch failed or the user interrupted, and the same at every core count. The serial path's chains also call `set.seed()` at their start; the handler's reset after that is idempotent. An earlier draft performed the parallel path's reset after dispatch and registered only the restore, so an interrupt during dispatch would have skipped the reset and left the two paths in different states under Box-Muller. The parent runs no random code after the chains: factor reparameterisation and diagnostics are deterministic.
- What restoring `.Random.seed` cannot do. Under the Box-Muller normal kind, R keeps the second deviate of each pair in a cache that is not part of `.Random.seed`, as `?RNGkind` documents, and changing the normal kind discards it. So a session in Box-Muller with a cached deviate pending gets a different next normal draw after a fit than if it had never fitted. Probed on 13 October 2026: identical `.Random.seed` before and after, next normal 1.3994 untouched against -0.3936 after a restore; under the default Inversion kind all three paths give 0.1836. The symmetric handling above makes the serial and parallel paths agree with each other under Box-Muller, which is the contract this design promises. What the session returns to is the state just after the chain seeds were drawn, not the state before the fit: the data preparation and the seed draws advance the stream, and running the chains does not advance it further. Agreement with that restored state holds for every normal kind except Box-Muller, and the help page says so in those terms. The test compares the next draws of `rnorm()`, `runif()` and `sample()` after the two fits, under the default kinds and under Box-Muller, not only `.Random.seed`.
- Independence by construction. A chain's randomness is fixed by its own two seeds alone, so it is the same whether it runs first, last, in process or in another process. No chain continues from where another stopped. That is the property the unexplained mirror observation in `TODO.md` ("Checks for Doug") singled out: 2 of 6 chains run one after another in one process entered a mirror labelling, against 0 of 16 run as separate processes. Whether the shared stream caused it is not known and this design does not claim to settle it; it removes the layout. Starting values stay common.
- The documented contract. `set.seed()` before `runOccJSDM()` reproduces a fit on the same platform and build. Fits with workers > 1 are identical to one another when every worker's BLAS runs single-threaded, which the package requests through the thread variables but cannot verify; the RcppParallel count does not affect the draws. They are identical to the in-process fit when the session's own BLAS is single-threaded too. R's reference BLAS, which CRAN's macOS and Windows builds install and which this machine runs, is single-threaded; whether a given installation really has it is a matter of provenance that the package cannot establish, so the help page tells users how `extSoftVersion()` indicates the library and that the indication is not proof. The package makes no identity promise across worker counts under any other BLAS: it records what it requested, and a user who has pinned OpenBLAS, MKL or Accelerate to one thread before starting R can expect agreement, but the package cannot confirm it. The shipped evidence, the benchmark, the refit and the final test runs, comes from an environment whose BLAS provenance was checked by inspection and recorded. A rounding difference inside a BLAS does not stay small in a chain of draws: it can flip a discrete sampling decision and send the rest of the trajectory elsewhere, so an in-process fit under an unpinned threaded BLAS can differ from the parallel fits wholesale, not by a tolerance. Reproducing a fit with `set.seed()` has always required a fixed BLAS configuration, and this design does not change that. The help page states the condition. Consecutive fits without resetting the seed differ, because the chain seeds come from R's RNG. A seeded fit's numbers differ from those of version 0.1.1 because every chain is now seeded on its own, including chain 1, whose R-level draws no longer continue the session's stream.
- What this changes elsewhere. Everything pinned to old numbers: the shipped `sampleresults` and its 7 October 2026 provenance, handled by the refit below; the quickstart's statement that the same seed reproduces `sampleresults`, true again after the refit, with its software line updated from R 4.5.0 to R 4.6.1; and the opt-in coverage snapshot in `tests/testthat/test-coverage-study.R`, which may need re-recording if a block moves by more than its 0.02 tolerance. No test pins fitted values to a seed; the tests assert that the same seed reproduces, that different seeds differ and that thread counts do not matter, all of which remain true. The lesson archives, the study records under `dev/simstudy` and the MCP pilot's pinned runtime are unaffected. A refit under the new code cannot be expected to match any archive made before it.

## The single-chain function

- Placement. A new file `R/chains.R` holds `run_one_chain()`, the task wrapper, the driver, the combination helpers and the cluster helpers. `R/runOccJSDM.R` loses the loop body and keeps the setup and the output assembly. The names below are indicative; the implementation plan fixes them.
- `run_one_chain(setup, seed_r, seed_cpp, chain)`. `setup` is one plain list built in `runOccJSDM()` from what the loop body reads: the model flags (`model`, `jsdmModel`, `threshold`); the data and index objects (`y`, `y_NA`, `M`, `K`, `P`, `sumM`, `sumP`, `sumK`, `maxP`, `primerId_p`, `idx_w_k`, `idx_p_k`, `idx_z_w`, `list_idx`, and the sizes `n`, `N`, `N3`, `S`, `d`, `g`, `gt`, `ps`, `ncov_theta`, `ncov_psi`); the design matrices (`X_theta`, `X_psi`, `Tr`); the precomputed spatial objects (`list_Xs`, `list_SoRSummaries`); the priors (`list_data`, `list_priors`, `a_theta0`, `b_theta0`, `a_p`, `b_p`, `a_q`, `b_q`, `b_betatheta`, `B_betatheta`, `spatial_sd_prior`); and the MCMC settings (`nburn`, `niter`, `nthin`, `summarisedLatentPresences`). The implementation plan fixes the exact list from a read of the loop. A PSOCK worker enforces it: a missing field is an error there, and the always-on tests run on workers.
- Body. The current starting-values block and iteration loop, moved, with four changes only. The seeds are set at the top. The latent-state means become per-chain sums of the retained `z`, `psi`, `theta` and `w`. The WAIC accumulators become per-chain, with the iteration counter running from 1 within the chain. The dead `theta_output_chain` allocation is dropped, since it would otherwise be `N * S * niter` doubles of `NA` per chain crossing the socket for nothing. Sampling order within an iteration and the message wording are unchanged.
- Output. A list with `draws`, the per-chain arrays as today; `latent_sums`, the four sums, or `NULL` where the model has none; `waic`, the three partial accumulators, `NULL` where the model has none, with their draw count; `elapsed`, in seconds; `chain`; and the two seeds.

## Workers

- Cluster. `parallel::makeCluster(workers, outfile = progress_file)`, PSOCK, with `parallel` added to `Imports` in `DESCRIPTION`. Immediately after creation an `on.exit()` handler registers the shutdown described under failures. No `clusterSetRNGStream()`: the chain seeds are explicit.
- Bootstrap, run once per worker through `clusterCall()`. The worker sets `.libPaths()` to the parent's, because a PSOCK worker inherits environment variables but not library paths changed at run time. It pins its thread count from the budget rule, through the environment variable and `setThreadOptions()`. Then it loads the same occJSDM as the parent. If the parent's namespace was loaded by pkgload, detected from the marker pkgload leaves in the namespace, the worker runs `pkgload::load_all()` with `compile = FALSE` on the parent's source path, which `getNamespaceInfo("occJSDM", "path")` gives. With `compile = FALSE`, pkgload (1.5.3 checked) skips compilation and loads the shared object the parent already built, so worker start-up can never compile and workers cannot race on a compilation. Otherwise the worker runs `loadNamespace("occJSDM")`. `pkgload` is not an import: that branch runs only when the parent was loaded by pkgload, which means pkgload is installed on the same library paths.
- Build identity check. Each worker reports four things: its occJSDM namespace path, its version, the md5 of its loaded shared object from `getLoadedDLLs()`, and a fingerprint of its loaded R code, which is every named function in the namespace, in name order, deparsed and digested with md5. Only closures enter the fingerprint. Native-routine bindings are excluded because they carry process-specific pointer addresses: compared across two fresh R processes loading the same installed build on 13 October 2026, 22 of the 172 namespace objects differed and all 22 were native-routine bindings, while the 146 functions were identical. Environments and R's own metadata objects are excluded too; the namespace currently holds nothing else, so functions are the whole of its R code. The parent computes the same four for itself, compares, and stops on any mismatch, naming both paths and saying which of the four differed. The shared-object md5 tests the compiled code. The R-code fingerprint tests the functions actually in memory, which the other three cannot: a parent loaded by pkgload, after an R-only source edit without a reload, keeps its old functions while fresh workers would load the newer source with path, version and shared object all matching; the parent then stops with a message to reload. The path catches library mix-ups. `deparse()` ignores source references and byte code, so the fingerprint depends on the code alone; checked on 13 October 2026, it is identical with and without source references and after byte-compilation, differs when a body changes, and takes about 20 ms.
- What crosses the socket. `setup` crosses once per worker, at bootstrap, through `clusterCall()`, and is stored in a package-level environment in the worker's occJSDM namespace. The task function is defined at package level in `R/chains.R`, so it serialises as a reference to the namespace, takes only the chain index and that chain's two seeds, and reads `setup` from the environment. It must not be a closure created inside `runOccJSDM()`: serialising such a closure would ship the whole frame of `runOccJSDM()`, including the preallocated full output arrays. The serial path stores `setup` in the same environment in the parent and calls the same task function one chain at a time in the streaming loop described under *Sequence in the parent*; the environment is cleared on exit in both paths.
- Dispatch, one chain per task. Chains are dispatched with `clusterApplyLB()`, one chain per task, in batches of `workers` chains; the parent copies each batch into the full arrays before dispatching the next. `parLapply()` is not used: it hands each worker a whole chunk of chains and runs them with `lapply()`, so a worker keeps every finished chain of its chunk in memory until the chunk returns, which with eight chains on two workers is four chains per worker. With one chain per task a worker holds one chain's draws at a time, and the batching bounds what the parent holds beyond the full arrays to one batch. Load balancing within a batch is harmless because the seeds are explicit: which worker runs chain k cannot affect the result.
- Sequence in the parent. Build `setup`; draw the seeds; save the RNG state and register the cleanup handler that resets and restores it; if workers > 1, create the cluster, bootstrap with `setup`, check builds, then dispatch in batches, copying each returned batch into the full arrays and releasing it before the next; otherwise loop over the chains in process, running the task function for one chain, copying its draws into the full arrays and releasing them before the next, which is the batching loop with a batch of one; combine the sums and accumulators; finish as today. The serial path never collects every chain's draws before copying.

## Combination, in the parent, in chain order

- Draws. Each chain's arrays are copied into the preallocated `[..., niter, nchain]` arrays at index k, as the loop does today. Which worker produced chain k cannot matter.
- Latent means. The per-chain sums are added in chain order and divided by `niter * nchain`. Same quantity as today, a different floating-point path, independent of `ncores`.
- WAIC. For each of the three accumulators the chains are merged pairwise in chain order with the standard formula for combining running means and sums of squared deviations. For parts A and B with counts nA and nB and n = nA + nB: delta is meanB minus meanA; the merged mean is meanA + delta * nB / n; the merged M2 is M2A + M2B + delta squared * nA * nB / n; the likelihood means combine as a count-weighted average. Then `compute_waic()` as today with `niter * nchain` draws. The current check that the counter equals `niter * nchain` becomes a check that every chain reports `niter` draws. The merged value differs from today's single pass in rounding only.
- Afterwards, unchanged: factor reparameterisation on the full arrays, the output lists, `computeDiagnostics()`, `infos`.

## Failures, interrupts and memory

- Error in a chain. The task wraps `run_one_chain()` in `tryCatch()` and returns a structured failure holding the chain number and the message, instead of letting the generic "one node produced an error" of `parallel` surface. Base `parallel` delivers results only once every chunk has returned, so the parent waits for the running chains and then stops with "Chain k failed: message". The worker's own output, including any traceback, is in the progress file.
- Shutdown on every exit, normal, error or interrupt. The `on.exit()` handler calls `stopCluster()` inside `try()`, then `tools::pskill()` on the worker PIDs recorded at bootstrap, unconditionally. The `try()` is load-bearing: `stopCluster()` throws "invalid connection" when any worker connection is broken, and an uncaught error there would skip the PID cleanup. Reproduced on 13 October 2026 with two workers: closing one connection made `stopCluster()` error and left the other worker alive until `pskill()` ended it. The PID step matters in the ordinary case too: a worker that is mid-chain reads the stop message only after its chain finishes, so without it, pressing Escape in the parent would leave the workers computing to the end of their chains. `pskill()` on a worker that has already exited is a harmless no-op.
- Memory. Each worker holds `setup` plus one chain's arrays, because dispatch is one chain per task; the earlier draft said the same but relied on `parLapply()`, under which a worker would have accumulated every chain of its chunk. The parent holds `setup`, the full arrays and, while assembling, one batch of returned chains: one chain in the serial path, as today, and `workers` chains in the parallel path, so the parallel parent's peak beyond today's full arrays plus one chain is `workers` chains, and when `nchain = workers` that is briefly about twice the draws. Each returned chain is dropped as soon as it is copied, in both paths. The benchmark measures the parent and the workers separately, and its `ncores = 2` run of four chains, where each worker runs two chains in turn, is the chains-outnumber-workers case; the report gives its worker and parent peaks on their own.

## Risks and open points

- The tier-1 time budget: cluster starts in the always-on tests are measured during implementation, and more cases move under `skip_on_cran()` if the 30 seconds are exceeded.
- Worker start-up never compiles, because the workers call `load_all(compile = FALSE)`. A parent whose loaded R code no longer matches its source tree is stopped by the fingerprint check rather than silently mixed with workers on the newer code. A parent whose shared object is stale relative to `src/` is not detected, because the workers load the same stale object; that is the developer's ordinary reload discipline and is not guarded.
- The parent's peak memory at assembly, one batch of `workers` chains beyond the full arrays, so about twice the draws when `nchain = workers`, is the price of collecting whole chains through the public `parallel` API. If the benchmark shows it matters at realistic sizes, chains could be collected one at a time with the lower-level functions of `parallel` in a later change.
- Windows: `makeCluster()`, `outfile` and `tools::pskill()` are documented to work there; not run here.
- Threaded BLAS: a session with an unpinned OpenBLAS, MKL or Accelerate can give an in-process fit that differs from the parallel fits, not by a tolerance but as a different trajectory once a discrete draw flips. The workers are asked to run single-threaded through the thread variables, but those are requests that other variables can override and that base R cannot verify, and the package cannot verify which BLAS it is running on either, since a replacement can carry the reference library's name. The help page scopes the promise to a single-threaded BLAS and says the indication is not proof; the identity test runs only where the maintainers have checked provenance and declared it; and no threaded-BLAS configuration is available on this machine to verify against.
- The WAIC merge changes the floating-point path of a value that also changes with the seeds; its correctness is covered by the unit test against the single pass.
